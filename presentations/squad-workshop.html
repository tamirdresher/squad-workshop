Orientation

Inspectable memory

.squad/team.md, .squad/routing.md, .squad/decisions.md, and agent histories.

More agents can mean more coordination and cost. Ask what changed, who owned it, and which check ran. See the orientation guide and PM track for plain-language explanations.

Module 1 · Product contract first

Give the team an outcome, then inspect its decisions.

I'm a solo developer building a small full-stack app called "Reading List."
Use a lean team: Lead, Backend, Frontend, Tester, and Scribe.
Stack: .NET 10 minimal API, React with TypeScript, and simple SQLite storage.
Keep architecture boring and maintainable.
Set up the team now.

Approve the proposed team. Continue with the module's product spec, implementation, architectural decision, and review prompts.

A decision needs a tradeoff and rationale, not just a file bearing the word “decision.”

Ask PMs to restate acceptance criteria before implementation. Follow the module instead of expanding the app. Keep permissions intentional; broad approval is not needed to understand the team model.

Module 1 · Review checkpoint

A generated app is a claim until you run and review it.

Behavior

  • Run the backend and frontend using the generated app's documented commands.
  • Exercise the requested reading-list flows.
  • Run its actual tests and inspect their assertions.

Team artifacts

  • Find the cast and routing.
  • Inspect the recorded architectural decision.
  • Compare the diff with the agreed spec.
  • Ask for corrections before accepting.

Use the generated project's real commands; do not invent a successful test receipt.

The workshop does not prescribe a prebuilt project layout. Have the team report exact commands and results. An agent review does not replace the human acceptance decision.

Module 2 · Compounding Memory & Second Feature

Does the second iteration reuse what the first learned?

Add these features and update everything accordingly:
1. Filter books by unread/read status (both API and UI)
2. Validation rule: title is required, author is required
3. Update all existing tests and add new ones for the filter and validation
4. Update the UI to show a filter toggle (All / Unread / Read)

Use the same learner repository. Watch whether agents retrieve prior decisions, preserve existing behavior, and test regression risks.

Record whether context was reused or had to be supplied again.

Follow Module 2. If restarting Copilot, relaunch inside the learner repository without reinitializing Squad. A faster response alone does not establish memory reuse; inspect the cited artifacts and resulting behavior.

Module 2 · Artifact review

Useful memory survives a skeptical read.

Inspect

Get-Content .squad\decisions.md
Get-Content .squad\routing.md
Get-Content .squad\team.md
Get-ChildItem .squad\agents -Recurse -Filter history.md
git diff

Ask

  • Would I write these notes for myself?
  • Which prior constraint affected this change?
  • Do filter and validation tests prove the requested behavior?
  • Did the original app keep working?

An empty decisions inbox can be normal: Scribe may have merged it into decisions.md.

Use Module 2's PM artifact rubric. If you already committed, inspect the relevant commit diff rather than an empty working-tree diff. Review before publishing learner changes.

Module 3 · Observability & Ralph Watch/Loop

See the work before you automate more of it.

Observe

Inspect team artifacts, agent output, issue routing, changed files, and executed checks.

For optional dashboard or external integrations, follow Module 3 and prepare the extra dependencies first.

Separate signals

Configured is not running. Running is not correct. A passing check is only evidence for what it actually tests.

Teams/email monitoring requires a configured bridge; it is not automatic access.

Do not spend the core workshop debugging optional infrastructure.

Keep this a facilitator-led tour unless the group has the prerequisites and time. The facilitator guide explicitly permits skipping unconfigured bridges.

Module 3 · Bounded operations

A recurring loop changes the risk, not the review gate.

Watch: issue-oriented work

Module 3 introduces squad watch for Ralph's polling workflow.

squad watch --help

Check installed help before using execution flags or monitoring integrations.

Loop: prompt-driven housekeeping

squad loop runs scheduled prompt-driven work.

squad loop --help

Define one task, permissions, a stop procedure, and review ownership before starting.

Keep execution facilitator-led, protect branches, and review every proposed change.

The module preserves historical watch examples and numbered issue caveats. They are not a guarantee of current installed behavior. Verify available commands and flags; if the installed release differs, explain the difference and do not run an unsupported example. Do not start an unattended recurring task from these slides.

Module 4 · @copilot, Presets & Cross-Squad

A cloud coding teammate still needs a bounded issue.

Add the teammate

squad copilot --auto-assign

Follow Module 4 for setup, issue delegation, and pull-request review.

Distinguish execution paths

Ralph's local execution and GitHub's @copilot coding agent are different paths.

A cloud task requires repository access and coding-agent availability. You review the resulting pull request.

One owner, explicit acceptance criteria, and no implied permission to merge.

Do not assign a real remote issue during a slide walkthrough without agreeing its scope and access. Adding a roster entry is not proof of a completed cloud run.

Module 4 · Reuse and delegation

Reuse the roster. Make each handoff inspectable.

Presets

Reuse a team setup rather than recasting every project from scratch.

Follow the module's squad preset examples and inspect what the preset installs.

Cross-squad

Use the module's peer registry, squad discover, and squad delegate walkthrough.

Give the receiving team an owner, bounded task, expected output, and a review gate.

Sub-squads are an ownership and workspace pattern, not a promised “sub-squad” command.

Check installed help before demonstrations. Explain peer squads and worktrees using the module's existing material; do not provision additional repositories or machines just for the slides.

Debrief

A working app is only half the outcome.

Implementation and evidence

Reading List app, second feature, behavior checks, architectural decision, and a reviewed diff.

Be precise about what ran and what remains unverified.

Judgment

Where did the team help? Where did it repeat itself? When would one assistant be simpler?

Choose the next optional module based on a real need, not the number of agents available.

Do not outsource the definition of done.

Ask for one failed assumption caught by a test or review. Distinguish a local exercise from production readiness and agent claims from observed results.
