Before Lab 2

Small feature. Explicit failure cases.

One endpoint, one UI action

PATCH /api/books/{id}/read
{"isRead": true}

Response: updated book. Unknown ID: 404. Missing or invalid boolean: 400.

Tests that can disprove success

  • Repeat the same PATCH: no extra side effects.
  • Read state survives an API restart.
  • Missing book is not silently created.
  • Title/author validation still holds.

A passing starter suite does not prove a feature that it never tests.

The important property is idempotence: assigning true twice leaves the same state. A toggle-only API would violate that contract. Keep both backend and frontend changes bounded. Inspect the response schema as well as status codes.

Lab 2 · minutes 60–95 · 35 minutes

Route implementation and regression tests.

Objective

Implement the read-state contract without weakening validation or changing the book schema.

Do this

Give a bounded spec. Assign implementation and test responsibilities. Inspect the diff, run checks, then record the decision.

Prompt skeleton

Add PATCH /api/books/{id}/read and a UI read control.
Require an explicit boolean and idempotent assignment.
Test 404, invalid input and persisted repeated requests.
Preserve title/author validation. No remote writes.
Report changed files and exact check results.

Success criteria

Read control works; missing ID and bad input fail correctly; repeated PATCH and restart checks pass.

Follow here

Learner guide · Lab 2

Today's decision

Title and author stay trimmed, required and at most 120 characters. PATCH assigns an explicit read state idempotently. Filtering never changes stored data.

Capture the source cited, the behavior preserved and the check that proves it.

Scribe may consolidate the inbox into decisions.md; an empty inbox does not mean the decision vanished. Inspect the installed version's actual paths. The evidence test is retrieval plus application, not a guessed directory name.

Second iteration, same invariants

Read a subset. Don't rewrite the list.

Request behavior

GET /api/books
GET /api/books?status=all
GET /api/books?status=read
GET /api/books?status=unread

Unknown status: 400. Same book schema. Stable ID order.

Preservation tests

  • One read and one unread book: exact subsets.
  • Default and all return the same list.
  • Invalid status does not mutate data.
  • PATCH and validation still pass.

Ask the team to find the prior decision before pasting it back into the prompt.

A filter implementation that marks everything read while querying is incorrect even if the screen looks plausible. Verify the full list and persisted states after each filter request.

Lab 3 · minutes 105–140 · 35 minutes

Make the second iteration earn its context.

Objective

Retrieve the recorded decision in a fresh session, then add all/read/unread filtering without regressing mark-read.

Do this

Record the cited source before implementation. Compare behavior and tests after the change.

Prompt skeleton

Find the prior read-state and validation decision.
Cite its file and explain the constraints first.
Add all/read/unread filtering and a UI selector.
Test exact subsets, invalid status and no mutation.
Preserve prior behavior. Stop for human review.

Success criteria

Cited decision + correct filter + unchanged PATCH and validation checks. Note if retrieval needed a hint.

Follow here

Learner guide · Lab 3

Manual route: inspect and apply the decision yourself. Do not label it autonomous retrieval.

Reserve five minutes to compare evidence. If the agent cannot retrieve the decision, document that observation; one precise hint is allowed but must be recorded. A new filter checkpoint recovers implementation, not evidence of live memory.

Lab 4 · minutes 140–166 · 26 minutes

Turn a claim into a review packet.

Objective

Inspect the feature diff, record the human decision and export only scoped evidence.

Do this

Stop your API and Vite. Run final checks and export. Review the diff against the spec. Record a finding or justify acceptance.

Course-root commands

.\scripts\Test-AiNextLab.ps1 -LabPath .\reading-list-squad-lab -Feature filter
.\scripts\Export-AiNextEvidence.ps1 -LabPath .\reading-list-squad-lab -Feature filter

Only mark-as-read completed? Use -Feature read in both commands; label filtering incomplete.

Success criteria

Actual test receipt, scoped source changes, decision-retrieval observation and explicit human accept/change outcome.

Follow here

Learner guide · Lab 4

Never export credentials, environment dumps, unrelated files or complete private chat transcripts.

Five minutes checks, ten review, six correction or justification, five export inspection. Keep owned API/Vite stopped through both commands: validation rebuilds the API and reinstalls frontend packages. Restart both before another browser review. Explicit filter/read selection prevents the starter marker from passing feature acceptance. A generated export is not itself proof that memory worked or review was independent. Learner observations must be labelled as such.

One course, honestly labelled routes

Fallback preserves practice, not provenance.

Live route

Entitled Copilot request succeeds. Observe routing, actual edits, decision retrieval and review behavior.

Network, policy, entitlement, model access and quota must all cooperate.

Prepared/manual route

Materialize a checkpoint, inspect or edit code, run tests, apply the decision manually and review the diff.

Still needs approved dependencies/tooling unless pre-staged. Not "offline AI" or proof of agent memory.

Record which route produced each piece of evidence.

Prepared checkpoints are a recovery tool and an accessible path for participants without entitlement. Do not mark learning evidence as live if a checkpoint supplied the implementation.

Advanced briefing · wrap, not another lab

A loop changes the risk, not the review gate.

Know the current commands

squad triage polls for issue work; --execute adds execution.

squad loop runs a prompt file; it does not require an issue queue.

configured selects normal vs onboarding flow. False/missing still executes; it is not a safety gate.

Before enabling either

Define one queue/task, explicit permissions, concurrency/time bounds, an operator stop, and a human review gate.

No live recurring loop, automatic permission grant, push or merge in this course.

Read installed help. Do not copy historical watch flags or stop-file recipes untested.

For 1.1.0, triage defaults to ten-minute polling and documents Ctrl+C. Loop uses loop.md by default. configured:true selects normal flow; false/missing selects onboarding and continues execution, not a safety/authorization gate. Present the difference; do not start either during the class. Stronger isolation and an approved operational runbook belong in a follow-on session.
